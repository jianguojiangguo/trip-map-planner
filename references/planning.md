# 行程策划：① 定输入 → ④ 校核

这份文件是 `SKILL.md` 五段流程里 ①–④ 段的正文。⑤ 交付见 `map-build.md` 与 `delivery.md`。

读它的时机：准备排一份行程时，从头读一遍；或者在某一关卡住时，只读那一段。

---

## ① 定输入 · 约束边界

### 1.1 要收到什么

**最少要有**（缺了没法开工）：

- 出发 / 返程日期，到达 / 离开时刻
- 机场 / 高铁站的**航站楼或站台**（决定当天实际可用时长）
- 想去的点、明确不想去的点

**最好再给**（有则大幅提高质量）：

- 人数、年龄段、有无长辈小孩
- 吃饭预算、能否排队、一天能走多少路
- 主题偏好（见 1.3）、节奏、体力
- 行李多不多、交通偏好、愿不愿意早起
- 住宿：**位置或大致区域**（不是具体酒店名——见 1.4）

### 1.2 输入模板

直接发给用户，让他填空或发截图，比逐条问快：

```
时间：
到达：
回程：
住宿区域：          ← 只要片区，不用具体酒店
人数：
年龄段：
一定要去：
可以去：
不要去：
主题偏好：          ← 从 1.3 的词表里选 1–2 个
节奏：              ← 轻松 / 适中 / 紧凑
能走多少：
餐饮预算：
能否排队：
补充：
```

截图（机票 / 已订酒店 / 收藏清单）通常比打字更快，优先接受截图并自行提取。

### 1.3 偏好：主题是第一维度

主题轴是**目标函数**——它决定"要做什么"。选错了不是少看一个点，是整趟白排。

**12 项词表**（选 1–2 个作主轴，其余作副轴；选不出主轴时用「混合」兜底）：

| # | 主题 | 典型内容 | 普查时会往哪捞 |
|---|---|---|---|
| 1 | 历史人文 | 古迹 / 古城 / 博物馆 / 历史街区 | 文保单位、博物馆名录 |
| 2 | 文学艺术 | 作家故居与足迹 / 作品中的真实地点 / 书店·咖啡馆 / 美术馆·剧场 | 故居、纪念馆、独立书店 |
| 3 | 自然山水 | 山岳 / 湖泊 / 森林 / 海岸 / 地质 | 风景名胜区、地质公园 |
| 4 | 市井民俗 | 老城街巷 / 市集 / 非遗与手作 / 节庆 / 民族村落 | 历史文化街区、非遗名录 |
| 5 | 美食风物 | 本地菜系 / 小吃 / 茶酒 / 产地与物产 | 老字号、菜市场、产地 |
| 6 | 建筑园林 | 古建 / 近代建筑 / 园林 / 宗教建筑 | 各级文保建筑、园林 |
| 7 | 工业遗产 | 老厂房 / 矿区 / 铁路 / 水利 | 工业遗产名录、改造园区 |
| 8 | 红色纪念 | 革命旧址 / 纪念馆 | 爱国主义教育基地 |
| 9 | 亲子研学 | 科普馆 / 动植物园 / 体验工坊 | 科技馆、研学基地 |
| 10 | 户外运动 | 徒步 / 骑行 / 水上 / 滑雪 | 步道、绿道、户外基地 |
| 11 | 演出体验 | 实景演出 / 戏曲 / 手作工坊 | 剧院、非遗工坊 |
| 12 | 混合 | 无明显主轴，以冷热搭配与顺路为先 | 兜底项 |

**边界说明**（避免用错）：

- **主题 ≠ 价值标签**。"出片 / 冷门 / 免费"是附加属性，不占主题位；
- **主题 ≠ 节奏**。"特种兵 / 休闲度假"属节奏，另设一项；
- **主题只到这一层**，不再往下分"玩法"。"跟着某本书走一遍"是对主题的用法，不另设层级。

**其余偏好项与用法**：

| 项 | 取值 | 怎么用 |
|---|---|---|
| 节奏 | 轻松 ≤3 点/天 · 适中 4–5 · 紧凑 6+ | 决定每天点数上限 |
| 体力 | 步行耐受、能否爬坡、能否久站 | 影响点型与点间距离 |
| 预算 | 门票 + 餐饮 + 交通的大致档位 | 影响取舍（贵的先砍） |
| 忌口 / 特殊需要 | 饮食、过敏、随行老幼 | 餐饮与点型筛选 |
| 已排除项 | 明确不去的 | 直接不进候选池，免得反复推荐 |

> **偏好必须先定，且要当筛选条件用。** 只把偏好读一遍、选点时却不拿它筛，等于没定。
> 检验方法很简单：候选池里的每个点，能不能说出它匹配哪条偏好；说不出的，就是清单驱动而不是偏好驱动。

### 1.4 顺序：偏好在前，住宿在后

**住宿是设施，后置于片区。**

出行的目的通常是景点，**住宿依附于景点与片区**。正确顺序：

```
主题偏好 → 选点 → 片区与动线 → 住宿综合决策（位置 · 价位 · 通勤 · 停车）
```

**先有景点路线，才有酒店选点**——不是先订酒店再凑行程。

> **例外分支**：住宿已订且不可改时，它变成一条**既定约束**，允许回头影响片区划分
> （换了城区，动线要重排）。但决策主导权始终在景点路线这边——**住宿是被综合选出来的，不是行程的前提**。

所以在 ① 阶段，住宿只收"区域/位置"这种粗信息；到 ③ 编排完成后再定具体住宿。

### 1.5 判断的先后

输入收齐后，按这个顺序过一遍——顺序本身就是优先级：

1. 天数够不够
2. 住宿（或用户活动重心）在哪 → 决定片区怎么分
3. 用户明确讨厌什么 → 先划掉
4. 哪些点看天气
5. 哪些点需要预约 / 限流
6. 哪些点会在节假日爆炸
7. **最后才补餐厅和咖啡**

## ② 摸家底 · 候选池

### 2.1 为什么必须普查

**起点不是"用户清单"，是区域资源。**

只从用户清单或模型记忆里选点，就是**记忆驱动**——能"想起来"的永远只是著名景点，这是采样偏差，**必然漏项**。

而漏项在用户侧是硬伤：不是"这版不够好"，是"**我点名要去的地方根本没排进去**"。

普查做的事，本质是**把选点从"记忆驱动"换成"清单驱动"**。

### 2.2 五个来源

| 来源 | 摸什么 | 解决什么偏差 |
|---|---|---|
| 行政区划逐级下钻 | 市 → 区 / 县 → 镇 / 街区 | 不漏县域、不漏下辖 |
| 地图 POI 分类型检索 | 名胜 / 博物馆 / 古迹 / 公园 / 街区 / 夜市 / 演出 | 主流的都在 |
| 官方名录 | A 级景区 / 文物保护单位 / 历史文化街区·名镇名村 / 非遗名录 | 有身份的点不遗漏 |
| 口碑侧反查 | 点评 / 小红书按"区域 + 主题"捞 | 地图搜不到的小店与新晋点 |
| 两端锚点 | 高铁 · 机场 · 码头（动线端点）+ 住宿候选 | 定首尾两天的形态 |

**检索维度由本次主题偏好决定**：这次主题是"文学 + 市井"，就按这两个主题去捞。
不是固定四类，也不是把能搜到的全捞进来——**主题轴决定检索清单**。

### 2.3 候选池字段

每个点必填，缺一项后面就会卡住：

| 字段 | 为什么必备 |
|---|---|
| 名称 | — |
| **主题标签** | 从 12 项里取；用于筛选与卡片标签 |
| **功能角色** | 从 6 角色里取；决定配比与地图图标 |
| 区位（行政区 + 坐标） | 坐标要 GCJ-02 或可换算；片区聚类靠它 |
| **建议游览时长** | 时间轴的第一块砖，没有它算不出"当天塞不塞得下" |
| 开放时间与闭馆日 | 决定放在时间轴的哪个窗口 |
| 是否预约 / 限额 | 进 ④ 的"可进入"关 |
| 热度与冷热时段 | 决定排在一天中的哪一段 |
| 交通可达性 | 最近地铁 / 公交 / 停车，决定段间方式 |
| **来源与查证日期** | 政策与时间会过期；没日期的信息不敢用 |

### 2.4 平台可用性

实测记录（2026-09 复查）：

| 平台 | 状态 | 备注 |
|---|---|---|
| 搜索引擎 · 携程攻略 · 文旅厅官网 · 新闻 | ✅ 可用 | 官方信息优先 |
| 小红书 | ✅ 可用 | 2026-09 复查，此前的 IP 风控已解除 |
| 大众点评 | ⚠️ 可能需登录 | 需登录态时走浏览器 CDP 抓 |
| 马蜂窝 | ❌ WAF 拦截 | — |
| 十六番 | ❌ APP 独占 | — |

> 平台状态会变（风控、登录策略、改版），属**时效性信息**：用之前先探一次，并把复查日期记下来。
> 具体检索工作流见 `research.md`。

### 2.5 什么时候算摸够了

三条自检：

1. **行政区划有没有下钻到底**——市辖区、下辖县、重点镇，都过了一遍？
2. **每个主题有没有各自的候选**——主轴主题只有两三个点，说明没搜透；
3. **有没有"用户会问的那种点"**——就是那种"你们怎么没排 XX"的点。有，就补进候选池。

## ③ 编排 · 两轴对齐（核心）

**一份行程 = 一张空间图 + 一个时间轴。** 两条轴各自成立还不够，要能互相换算。

| | 空间轴 | 时间轴 |
|---|---|---|
| 输入 | 候选池的区位 | 候选池的时长与开放窗口 |
| 操作 | 片区聚类 → 排顺序 → 定交通方式与路径 | 开放窗口 → 游玩时长 → 段间交通 → 用餐 → 缓冲 |
| 产出 | 动线（不折返） | 当天时刻表 |
| 约束 | 片区不打架、路径真实存在 | Σ ≤ 当日可用时长 |

### 3.1 空间轴：片区 → 顺序 → 路径

1. **片区聚类**：把候选池按地理位置归堆。一天一个主区域（见 3.5）——这是**动线成本最低**的排法：换乘少、吃饭好插、人累得慢、临时改也容易。
2. **排顺序**：在同一天的片区内部，让点连成一条不回头的线。判断方法很直接——**把点按编号画到图上，看线有没有交叉或折返**。
3. **定路径**：用真实路网（OSRM）算，不画直线。直线会让人误判距离，把"跨江 40 分钟"看成"直线 5 公里"。

### 3.2 时间轴：五段相加

当天的时间预算由五块组成：

```
开放窗口（能不能进）
  → 游玩时长（每个点多久）
    → 段间交通（点与点之间多久）
      → 用餐（含排队）
        → 缓冲（迟到、找路、临时停留）
```

**关键前提**：游玩时长和段间交通时长**必须先有数**。没有这两个数，后面的加总全是感觉。

- 游玩时长的取值：普通景点 60–90 分钟，博物馆 2–3 小时，街区 / 市集 45–90 分钟；
  有明确讲解或演出的按场次算。
- 段间交通的取值：查实时路况或地铁用时，**不要按直线距离估算**；
  同城内通常 15–35 分钟一段，跨江 / 跨区可能 40–70 分钟。

### 3.3 咬合件

把两轴焊在一起的只有两件东西：

1. **顺次编号** —— 把时间顺序投影到空间上，折返会自己现形；
2. **段间交通时长** —— 把空间距离换算成时间成本，当天塞不塞得下才可算。

> 这就是"落图 + 编号 + 段间时长"的本质：**不是把行程画得好看，是让两轴能互相校核。**

### 3.4 配比：功能轴的数量约束

| 角色 | 数量约束 | 说明 |
|---|---|---|
| 核心目标 | 1–2 / 天 | 当天的主目标，值得为它安排半天 |
| 顺路穿插 | 1–2 / 天 | 沿途可停，不为它绕路 |
| 餐饮 | 1–2 / 天 | 含排队时长，要落进时间预算 |
| 休憩补给 | 按需 | 体力恢复点（茶歇、公园、咖啡） |
| 住宿 | 1 处 / 段 | 依附于片区（见 1.4） |
| 交通枢纽 | 按需 | 首尾两天的动线端点 |

**日计划粒度标准**：每天至少 3 个明确点位——**核心 1–2 + 顺路 1–2 + 餐厅 1–2**。
少于 3 个，一天撑不起来；超过节奏上限（见 1.3），走不完。

### 3.5 排布原则

- **一天一个主区域**——换乘少、吃饭好插、累了能撤。
- **一天最多一个重预约点**——两个硬时刻撞在一起，当天就没有弹性。
- **第一天下轻手**——落地、进城、放行李都要时间。
- **最后一天不跑远**——返程时刻是不可谈判的硬约束。
- **长距离点只放在非节假日**。
- **户外点标天气敏感，优先配附近室内备选**。
- **点名要去的核心地标，单独成节点 + 明确时段**；别只排成"顺路经过 / 在附近吃饭"——那样等于没去。
- **优先把它排在人最少的时段**（开门即到、或午后散场）。

### 3.6 一天的样子（示例）

| 时段 | 内容 | 时长 |
|---|---|---|
| 08:30–09:00 | 住宿 → A（地铁 2 站） | 30 |
| 09:00–10:30 | A 核心目标（开门即到，人少） | 90 |
| 10:30–10:50 | A → B（步行） | 20 |
| 10:50–12:00 | B 顺路穿插 | 70 |
| 12:00–13:30 | 午餐（片区顺路，含排队） | 90 |
| 13:30–14:00 | 餐后 → C | 30 |
| 14:00–16:00 | C 核心目标（需预约，已约） | 120 |
| 16:00–16:30 | 缓冲 / 茶歇 | 30 |
| 16:30–17:00 | C → 住宿 | 30 |
| — | **当日合计** | **约 8.5 h** |

> 表里每一段都要能说出依据（时长从哪来、交通方式是什么）。
> 加总超过当日可用时长 → 回 ③ 删点，不要硬塞。

## ④ 校核 · 三硬两软

排完不算完，要过一遍验收。

### 4.1 三硬

**任一不过 = 那天不成立。**

| 判据 | 归属 | 怎么验 |
|---|---|---|
| **可达** | 空间轴 | 点连得起来：不折返、片区不打架、交通方式真实存在（有地铁 / 有班次 / 不封路） |
| **可容** | 时间轴 | Σ(游玩 + 段间 + 用餐 + 缓冲) ≤ 当日可用时长 |
| **可进入** | 准入 | 需预约 / 限流的点，**那天的名额确实拿得到**；有硬时刻的（航班、演出）不撞车 |

### 4.2 两软

决定"值不值"，不决定"跑不跑得通"。

| 判据 | 内容 |
|---|---|
| **合意** | 点匹配主题偏好；冷热时段搭配合理；餐饮落位在当天片区 |
| **抗扰** | 天气敏感点有室内备选；信息（政策 / 时间 / 票价）标了查证日期，过期复核 |

### 4.3 不过怎么处置

只有三种动作：

| 情况 | 处置 |
|---|---|
| 可达不过（折返 / 跨区） | 换天、或把点移到它所属的片区那天 |
| 可容不过（塞不下） | 删点（优先删顺路穿插、次删软目标） |
| 可进入不过（约不到） | 换锚点（改期）、或换备选点 |
| 抗扰不足 | 补室内备选；补不了的，**明说它是天气赌注** |

**删点要说明**：删了什么、为什么删。行程不是越满越好，是越顺越好；用户有权知道被删的理由。

## 交付前的最后一道：行程文档

### 输出模板

```
先说结论
  （几天、主轴是什么、整体怎么走、有几个硬时刻）

每天怎么走
- Day 1 / 主区域 / 点位顺序（含编号）/ 每段交通方式与时长
- Day 2 …
- Day 3 …

每天吃什么
- 午餐区域 / 主推候选 / 近距离备选
- 晚餐区域 / 主推候选 / 近距离备选

天气敏感点
提前订什么      ← 与票约台账同源
删掉什么，为什么
为什么这样排
```

地图页与票约台账是同一份方案的另两个载体，见 `map-build.md` 与 `delivery.md`。

### 常见坑

- 一股脑把用户清单全塞进去
- 把出发前的计划当成旅途中必须执行的脚本
- 不看节假日、不看天气敏感点
- 不看航站楼、不看最后一天返程时间、不看住宿位置
- 用社媒内容当营业时间（社媒只补感觉，不能当事实）
- 为了名店把整天卡死
- 给出"什么都想要"的行程

### 核心原则

**不端水。要替用户删东西。行程不是越满越好，是越顺越好。**

行程是出发前的**参考坐标**，不是旅途中必须执行的脚本。真实执行时，天气、当前位置、体力、饥饿程度都可以覆盖原计划。
计划的价值是给 agent 和用户一个清楚的基准：今天在哪个区域，哪些点是锚点，哪些点可放弃，吃饭在哪里找。
