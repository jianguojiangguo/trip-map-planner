# 交付：准入台账与发布核查（⑤ 交付）

这份文件覆盖 ⑤ 交付里除地图本身之外的部分：**票约台账**（第三个载体）、现场工具、以及**发布前核查**。

---

## 一、票约台账

### 1.1 为什么它要独立成一个载体

它管的不是"行程排得好不好"，而是"**行程能不能发生**"。

| 特征 | 说明 |
|---|---|
| 是**出发前要完成的动作** | 不是行程表上的一个点 |
| 有**时点 deadline** | 如"9/25 早 8:00 抢 10/2 的名额"，错过就没有 |
| 有**稀缺性** | 名额限流；抢不到 → 行程得改 |

> 所以它不是"提醒"，是**行程的准入台账**：哪些已约成、哪些待抢、抢不到的备选是什么。
> 图管「空间 + 时序」，台账管「准入」，两者并列。

### 1.2 内容构成

- **倒计时卡**：离最近的硬时刻还有多少天
- **日期网格**：按行程日期铺开，标出每一天的预约 / 抢票事项
- **分日期的可勾选清单**：勾选状态用 `localStorage` 持久化（现场少一次网络依赖）

### 1.3 实现要点

作为额外 tab（`data-day="99"`），`go(99)` 走自定义内容 + `showDay(0)`：

```js
panelsEl.innerHTML = idx===0 ? overviewContent()
                   : (idx===99 ? ticketContent() : renderDay(idx));
showDay(idx===99 ? 0 : idx);
```

> ⚠️ **`go()` 里必须显式加票约分支**。没有这个分支时 `go(99)` 会掉进 `renderDay(99)`
> → `TypeError: Cannot read properties of undefined (reading 'title')`。
> 这类 bug **光看源码 / 替换报告发现不了，只有真的点一下那个 tab 才暴露**
> → 自检脚本必须**真点一次票约 tab**，不能只数 DOM。

**tab 位置**：对外分享 / 演示的版本把「票·约」插到「总览」右边（`tabs.insertBefore(btn, tabs.children[1])`）；
9 个 tab 在 390px 手机上偏挤，自己用的可以放最右。

**日历起点 / 长度按关键日期重算**：如 `new Date(2026,8,20)` + 18 格 → 覆盖 9/20–10/7，
让最后一个行程日刚好落在末格。

**徽章要区分「抢票 / 预约 / 行程」**：给 `groupHTML(list, cat)` 加类别参数，
车票项在非行程日别标成「预约」（否则会出现"写着'预约'、内容是抢车票"）。
三色系：`.chip.rail` 砖红 / `.chip.book` 蜜桃 / `.chip.trip` 抹茶。

### 1.4 规则类数据必须实查 + 标查证日期

**旧数据会过期，这类信息每次都要重新实查。**

实战案例：某版原文写「荆州博物馆 · 免费 · 需预约 · 周一闭馆」，
但当地政府网 2026-09-21 公告已改为「国庆假期 10/1–7 正常开放并延时 8:30–18:30，**个人参观免预约**，刷身份证或支付宝扫码入馆」。

做法：把行程里每个「需预约」的点逐条过一遍官方渠道（政府网 / 官方公众号 / 官网），
再落进日历与清单，并在页脚**标注实查日期**。

> 顺带注意**周一闭馆 × 法定节假日**的组合：某日是周一但属法定假期 → 照常开放，
> 这类冲突要在清单里写清楚，否则用户会自己劝退。

## 二、现场工具

- **全屏地图切换**：`body.map-only #content{display:none}` + `#map{width:100%;height:100vh}`，
  切完调两次 `map.invalidateSize()`（80ms / 340ms）。
- **一键导航**：每个点位带导航链接（按名称搜索，或按坐标）。
- **断网可用**：地图库内联，不依赖 CDN（见 `map-build.md`）。
- **支付提示**：`pay: 1` / `pay: 0.5` 徽章，提示哪些点可能不支持常用支付方式。

## 三、发布前核查（把技能或地图公开发布之前）

要把这类成果发到 GitHub（尤其是基于他人开源项目的衍生版），先过 4 关。
**实战里这 4 关有 2 关是真踩到的**：

1. **先确认原作许可的"实际形态"，别假定仓库里一定有 LICENSE 文件**。
   看仓库页 About 栏是否显示 License；把 `LICENSE` 文件直接拉一遍。
   实战遇到：原作在 `README` 末尾写了一行 `MIT`，但仓库里**根本没有 LICENSE 文件**（API 返回 `license: null`）——
   属于"作者声明了、但没落成文件"。
   处理：**按作者已声明的许可办，同时在自己仓库补一份 MIT 全文**，原作者版权行放首位、自己的修改另起一行。
   这是 MIT 唯一的实质义务（版权声明与许可全文须随副本保留）；版权年份取仓库首次提交时间来定。

2. **逐文件比对，别拿"应该没改"当结论**。拉上游 `main` 上每个文件算 md5，跟本地副本对。
   实战抓到 `assets/template.html` 声称"逐字节一致"、实则差 1 行——而那 1 行正是上游已经修过的**白屏 bug**
   （本地拿的是旧副本）。**上游修过的 bug 不能跟着自己一起发出去**；发现本地比上游旧，就主动同步。

3. **自查有没有"过度声明"**。`README` / 改动清单里凡是写"与原版一致""未改动""+N 行""N 行 → M 行"的，
   都要能用脚本复算。**数字写错比不写更伤信用**。
   ⚠️ 顺序：**内容全部冻结后再统计**——先统计、后补内容，行数当场就过期。

4. **隐私扫描**。查绝对路径（`C:\Users\...`）、本机用户名、内部昵称、IP、手机号。
   分发前换成相对路径或通用占位；
   `127.0.0.1` / `localhost` 之类的回环地址属正常文档内容，可保留。

**发布方式的优先级**：

> **给上游提 PR 回馈 > 独立仓库（保留署名与许可声明）> 只分发自己原创的部分**

分享行程地图（而非发布软件）时，另有一关：**打码住宿名与个人信息**。
