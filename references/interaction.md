# 与用户对话：四拍格式

这份文件不属于五段流程的任何一段，它是**横切在整条流程上的交互规范**——
①–④ 里每一次需要用户决策的提问，都走这个格式。

---

## 四拍是什么

**Re-ground → Simplify → Recommend → Options**。缺一不可，顺序不可换。

| 拍 | 做什么 | 为什么 |
|---|---|---|
| **Re-ground** | 告诉用户"你在哪" | 用户可能 20 分钟没看屏幕，打开窗口第一眼必须是定位 |
| **Simplify** | 用大白话说清在问什么 | 不用术语、不用内部阶段名 |
| **Recommend** | 给一个明确推荐 + 理由 | 降低决策负担，没异议直接点 |
| **Options** | 2–4 个可点击选项 | label 自解释，遮住 description 也能选 |

---

## 典型场景

### 场景一：信息不足，需要收集

用户只丢了一句"帮我做个 XX 行程"：

```
Re-ground:  行程规划, Step 1: 基本信息
Simplify:   先搞清楚几件事，才能排行程。
Recommend:  建议先告诉我日期和住宿区域，其他我可以帮你选。

Q1 出行信息:
  A) 我发截图 — 机票 / 酒店截图丢过来，我自己提取
  B) 我打字说 — 我告诉你日期、住宿、想去的地方

Q2 人数和节奏:
  A) 两人，能走 — 标准节奏
  B) 带老人 / 小孩 — 放慢节奏
  C) 一个人 — 自由安排
```

### 场景二：删点确认

用户清单塞不下，需要砍：

```
Re-ground:  行程规划, 路线取舍
Simplify:   4 天放不下 12 个点，需要砍掉几个。
Recommend:  建议砍远郊，因为假期远郊交通挤、天数短来回浪费半天，留给下次专门去。

Options:
  A) 按你说的砍远郊（推荐）
  B) 我一定要去 XX，砍别的
  C) 让我看看完整清单再决定
```

### 场景三：餐厅风格

```
Re-ground:  行程规划, Day 1 晚餐
Simplify:   第一晚刚到，选什么风格的饭。
Recommend:  建议选落地型——离住宿近、出餐稳、不用排队，刚下飞机别折腾。

Options:
  A) 落地型（推荐）
  B) 打卡型
  C) 我有别的想法
```

### 场景四：迭代确认

行程排完，让用户过目：

```
Re-ground:  行程规划, 方案确认
Simplify:   上面是完整行程，看看方向对不对。
Options:
  A) 没问题，生成地图页面
  B) 我要调几个地方
  C) 大方向不对，重新来
```

## 关键原则

- **Smart skip** —— 用户指令已包含的信息，跳过对应问题。用户说了"两个人、不要某地、喜欢吃"，就别再问这三个。
- **问题合并** —— 没有依赖关系的问题，合并到一次交互。能一次解决的不拆成三次。
- **不问就默认** —— 非必要的探索性问题，用户没提就替他决定。**只问自己无法决定的事**。
- **严格区分 will 和 is** —— 还没执行的用"计划 / 接下来会"，已完成的用"已经"。
  说"已经生成"但实际没有，信任直接裂。
- **不替用户理解歧义问题** —— 用户问"XX 怎么样 / XX 的价值"，先确认**比较基准**（跟什么比、问的是不是只有这一件），再动笔。
  一次答偏比多问一句代价大得多。

## 反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|----------|
| 没有 Re-ground 直接问 | 用户不知道自己在哪 | 先说"行程规划, Day 1 晚餐"再问 |
| 列选项没推荐 | 选择瘫痪 | 推荐一个，说明为什么 |
| 要求用户打字回答 | 摩擦大 | 提供 A/B/C 选项 |
| 用户已经说清楚了还问 | 浪费时间 | Smart skip |
| 把未执行的说成已完成 | 摧毁信任 | 严格区分 will / is |
| 自己替用户理解歧义 | 答非所问 | 先确认口径再动手 |
